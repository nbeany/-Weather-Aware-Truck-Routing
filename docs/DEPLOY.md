# Deploying to Render

The recommended setup is **one Render web service** that serves both the React app and the
Django API from the same address. It is defined in `render.yaml` (a Render Blueprint) and
built from the root `Dockerfile`.

## How the single service works

- The Docker build compiles the frontend with Node, then copies `frontend/dist` into a
  Python image and pre-compresses it (`python -m whitenoise.compress`).
- WhiteNoise serves the frontend at `/` (gzip or brotli, with fingerprinted `/assets/` files
  cached permanently). Django handles everything under `/api`.
- The frontend is built with an empty `VITE_API_BASE_URL`, so the browser calls `/api` on
  the same host. No CORS settings are needed.
- Gunicorn runs one worker with four threads (`backend/gunicorn.conf.py`) so every request
  shares the in-memory weather cache, and binds to the `PORT` that Render provides.

## Deploy with the Blueprint

1. Push the repository to GitHub.
2. In the Render dashboard choose **New → Blueprint** and select the repository. Render reads
   `render.yaml` and proposes one free web service named `routecast`.
3. When asked, paste your `HERE_API_KEY`. `DJANGO_SECRET_KEY` is generated by Render and
   `DJANGO_DEBUG` is set to `false` by the Blueprint.
4. Click **Apply**. The first build takes a few minutes.
5. Open `https://<service>.onrender.com/api/health` and confirm `{"status":"ok"}`, then open
   the site root and confirm the header chip shows **Online**.

Pushes to `main` redeploy automatically (`autoDeploy: true`).

| Variable | Set by | Notes |
| --- | --- | --- |
| `HERE_API_KEY` | You, at Blueprint creation | Server-side only. Required for routing and place search. |
| `DJANGO_SECRET_KEY` | Render (`generateValue`) | Long random value. |
| `DJANGO_DEBUG` | Blueprint | `false`. |
| `TRUCK_TIME_FACTOR` | Blueprint | `1.0`; HERE's truck mode already models truck speeds. |
| `RENDER_EXTERNAL_HOSTNAME` | Render | Added to `ALLOWED_HOSTS` automatically. |
| `OPEN_METEO_BASE_URL`, `OPEN_METEO_PROXY_TOKEN` | You, optional | Use a weather proxy if Open-Meteo rate-limits Render's shared IPs (see below). |

## Run the production image locally

```bash
docker build -t routecast .
docker run --rm -p 10000:10000 -e PORT=10000 -e DJANGO_SECRET_KEY=local-only \
  -e DJANGO_ALLOWED_HOSTS=127.0.0.1,localhost -e HERE_API_KEY=<your key> routecast
```

Then open `http://127.0.0.1:10000/`.

## Alternative: separate backend and static site

The API still runs on its own when `frontend/dist` is absent, so the frontend can be hosted
separately:

1. **Backend web service:** root directory `backend`, build `pip install -r requirements.txt`,
   start `gunicorn -c gunicorn.conf.py config.wsgi:application`, environment
   `PYTHON_VERSION=3.12.0`, `DJANGO_SECRET_KEY`, `DJANGO_DEBUG=false`, `HERE_API_KEY`.
2. **Static site:** root directory `frontend`, build `npm ci && npm run build`, publish `dist`,
   with `VITE_API_BASE_URL` set to the backend origin (no trailing slash).
3. Set the backend's `FRONTEND_ORIGIN` to the exact static-site origin and redeploy it.

## Troubleshooting

- **Slow first request:** free web services sleep after 15 minutes without traffic, and waking
  up can take up to a minute. The frontend shows a "waking up" notice and retries `/api/health`.
- **"Weather service rate limit exceeded":** Open-Meteo's free tier limits requests per IP and
  Render's IPs are shared. Route Open-Meteo through a small proxy and set
  `OPEN_METEO_BASE_URL` (and `OPEN_METEO_PROXY_TOKEN` if the proxy needs one).
- **Error responses** are JSON and never include provider URLs, tokens or stack traces.
